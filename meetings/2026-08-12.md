* Immutable Releases vs Signed Releases
  * Once a project enables Immutable Releases, by definition you can't change a release
  * Observed in OIIO / OSL
  * Thus the workflow adopted by most ASWF projects to sign (source) releases doesn't work
  * Solution is roughly to:
    * Create a "draft" release
    * Upload the signed assets (tarballs, binaries)
    * Remove the "draft" status, which makes the release immutable
  * Both concepts are useful
    * Signed Releases allow end users to verify that an asset hasn't been modified during download / locally
    * Immutable Releases protect against unauthorized modifications on GitHub itself
  * Once the 3 step approach has been worked out, should be shared with other ASWF projects]
  * Andrew: you can't change tags, and you can't change a release. But you can change the release notes, and you can mark it as no longer the latest version. You can't get rid of it, but you can mark it as longer a current release. You can delete from your local repo, but not on GitHub. It is "immutable" as much as GitHub can make it immutable. Can't make a release with the same tag. But there are still aspects you can change as above.
  * Andrew: LF has been doing immutable releases or 4-5 months, workflow:
    * Create a "draft" release, we use release-drafter which creates draft releases with semver, guesses the version based on semantic version commit messages
    * Builds release notes based on PR comments
    * Build / testing / sbom artifacts attached to draft release
    * Finally mark the release as no longer draft, once that attribute goes away, then the release becomes immutable
  * Jon: can you rename it? Andrew: no, you can edit the release notes body, haven't tried the title. Jon: if for some reason it was determined there was a mistake, would be good to direct people away from it. Andrew: we only had one "bad" release, we marked it as "not the current release", so it doesn't show it as the current, but it is still available. We updated the release notes to say "don't use this release". Pre-pended a message to the release notes.
  * JF: I guess maliciously pulling a valid release would be bad. Andrew: once you make a release, it is set in stone. Also a way to help issues with supply chain issues. Primary target is GitHub Actions themselves, if folks set up their workflows correctly, they are either using the GitHub Actions at "main", which is bad, or use `@version` tag, which can move. A lot of attacks was to compromise a GitHub action, moving the tag to compromised version, then migrate a bunch of tags to the same malicious commit. Immutable releases stops those attacks, but still best to pin to SHA, a project may or may not be doing immutable releases. So still valid to pin to SHA for actions. Useful for software releases as well, but was primary architected for (reusable) GitHub Actions.
  * Andrew: signed releases and immutable releases go hand in hand. Artifacts will not change after the fact, and can validate that the signature is valid. A lot of our workflows have sigstore attestations which can be attached to builds, along with building sboms.
  * JF: if you automate building from a project, you have to change your automation to download the signed releases.
  * Andrew: GitHub automatically adds unsigned tarball / zip, we update a signed release with a release attestation.
  * JF: someone will have to figure out the new process. Andrew: you can do a manual draft to release in the UI, as long as the artifacts are already attached to the release. If automated, you need to have the draft release exist. External releases like PyPI / npm / ... are done after the fact and considered immutable. JF: is this release-drafter infrastructure re-usable? Jon: [release-drafter](https://github.com/release-drafter/release-drafter) Andrew: we use this with Semantic Version commits. Larry: I handcraft release notes, for our projects it's not enough to pull them from commit messages. Andrew: release-draft builds a template based release notes, but you can still update those manually. We can add notes manually. Larry: this is visible externally? Andrew: just to maintainers. A draft release is only visible to maintainers. Larry: at what point do the other artifacts get attached? Andrew: you create a release draft, artifacts get attached automatically, when you do the release itself, your release workflow creates all the artifacts and attaches them to draft release. Andrew: demo of lfreleng-actions/dependamerge, release-drafter.yaml runs on every PR. Runs the release-drafter action. We also use the harden-runner action. release-drafter uses a config file as a template, has the template for release notes, also auto labeler for PRs since it uses labels for release notes. It creates a draft release with a Draft tag. build-test-release.yaml workflow does the build and test again, in release section. Larry: can you override version numbers? Andrew: draft release numbering will be automatic based on semantic commit messages. Larry: people sometimes make messages. Andrew: if you detect the version is wrong, you can override it. Only supports CalVer or SemVer for tags. Also require that tags are signed.

Andrew: if you develop actions you think would be relevant, releng is also willing to pick them up. Larry: depending on how specific it would be to ASWF or not. Andrew: Python workflows are quite "magical", just drop a small config file into your project, zero configuration, and the actions figure it all it.

So we wanted to migrate those to GitHub Actions. JF: similar to the project health scanner.

* GPU runner NVIDIA driver update
  * OpenQMC is now using the GitHub T4 "larger" GPU runners
  * Flagged that the 2027 aswf-docker images can't be used: these include CUDA 13.3 which complains that the NVIDIA driver is too old
  * Current 610 series driver still supports T4 GPUs
  * In theory older CUDA versions (2023/2024 aswf-docker images have CUDA 12.6.3, so not that old)
  * What would be the process to update the NVIDIA driver on those images for GitHub:
    * Andrew: we're not providing an image, it is coming from GitHub. Jonathan: it's the driver that runs on the metal / VM. Andrew: it's something that GitHub would have to admin. JF: what about custom images? Andrew: there are still specific requirements, and may not support GPU runners. I have an engineer who knows how to spin up AWS instances without going through CodeBuild, with a cost. JF: is there a timetable from GitHub for newer driver support? Andrew: I can ask our GitHub rep. JF: I will create a LF ticket. Jonathan: CUDA 13 will be the last CUDA that supports the T4 GPUs. They are 8 years old at this point. At some point the T4 runners will drop off.
    * Larry: studio side maintainers may be constrained about CUDA versions, which cards will support which version, which DCC supports it... it's a real mess. The less dictating from VFX platform the better. Jonathan: wasn't advocating to mandate it.
  * Jonathan: OpenVDB nanoVDB CI
    * be able to request CodeBuild instance. We typically create a matrix of configurations
    * we're going to tack a conservative approach to support lowest version of CUDA we can
    * fvdb is a separate repo, takes a much more aggressive approach, newer CUDA / PyTorch versions, due to ML scientist audience
    * With use of codebuild, we authenticate with a secret added to repository. You can't get those secrets in a fork / PR, you can only get to them with pull-request-target trigger, not pull-request. How do people work like this? A pull-request trigger runs your CI in the source branch. pull-request-target dispatches from target of the PR, CI job definition comes from main branch. If you make changes to the job definition, it's not reflected when your job runs. You don't want someone to exfiltrate secrets, so that makes sense, but makes it hard for maintainers to update job definitions from a PR. How do we solve that at ASWF?
    * JF: you just "slam it into main"? Andrew: we don't have a good solution, one of my engineers have micro orgs for everything they are working on, if they are doing work which deals with secrets, they do the work in a "micro org" with access to secrets, test it, then on PR they can point to their own micro org to show that something worked.
    * Jonathan (chat): if your engineer wants to have a look, here’s that setup in fvdb-core for running any arbitrary EC2 instance: [EC2 instance](https://github.com/openvdb/fvdb-core/blob/main/.github/workflows/cu130.yml)
    * Andrew: this is one of my biggest complaints about GitHub Actions, hard to test. No way to designate a "trusted repository", would require back end changes they don't currently have.
    * Jonathan: we may have a feature branch, open a PR between feature branch and master and allow CI to run again.
    * Jon: we've been doing that too, change the branch the CI runs on from main to branch, when happy change it back to main. In Moonray we don't have CI yet, don't want to have a bunch of churn, so I just copied (not forked) the repo, made it internal, pushing directly to main and see what happens. No one outside maintainers have visibility. Then copy back when done. Not CUDA back end for now. But in general how we deal with GHA without being in main branch.
    * Jonathan: wondering if it would be worth investing in building a bot to handle this, figure out a way to open PRs from forks. Jon: Moonray likely to have this problem. JF: maybe there's an existing solution out there? Jonathan: I've done a lot of investigation, bot solution seems the best, but the one inside NVIDIA is pretty custom. Haven't seen anything else that helps. Andrew: could have a bot triggered by a comment from an authorized person. We have a lot of comment triggered workflows from Jenkins days, allow people to leave a comment to validate that it is authorized. So a comment trigger to run a job. But still won't fix issue when a workflow is fixed in PR. Has to come from a branch in the same repository when you want to deal with secrets. Could have comment based workflow take the PR and raise it into a local branch to validate it, then close that PR / branch when done. A lot of moving parts... Jonathan: the NVIDIA bot does something like that, could put the maintainer in touch with your engineer. Open PR from fork. bot copies the branch, waits for a maintainer to authorize, then runs the CI. The bot takes care of syncing the fork branch to the repo local one.
